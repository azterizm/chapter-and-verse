# S5.1a Token budget measurement (F12): requirements

Groq free tier allows 8,000 tokens a minute. On 24 Nov one answer made 3 to 6 calls of about 1,400 prompt tokens each (57 to 63% premise), so Groq held about one answer a minute and close questions spilled to Cloudflare (slow tail). Before changing anything we need exact numbers, and a tool that re-measures them after each change (the S5.1 gate is "answers per minute on Groq at least doubled on paper").

- R1 Module `eval/token_budget.py`, run as `uv run python -m eval.token_budget --split dev [--battery PATH] [--out DIR] [--judge-scope all|cited] [--dense-dir DIR]`. No network and no provider calls: build the pipeline as `eval/legal_gate.py` does for the retrieval gate (import its builder, do not copy it) but with a capturing rotation that records every `ChatRequest` it is given and then fails the way `NoModelRotation` does, so the real first generate request is captured with its real messages.
- R2 Per legal battery row (rows whose `must_reach` is non-empty), report: windows sent (count, total characters), the captured generate request (system and user characters, the ledger's `estimate_tokens` from `chapterverse.providers.ledger`, the plain 4-characters-a-token count from `chapterverse.audit.prompt.estimate_tokens`, `max_tokens`), and the premise share (characters of the rendered passages over all characters).
- R3 Judge calls: build the real judge messages the verifier sends for one sentence (read `legal_rag_verifier.judge` read-only to find the message builder and use it, do not re-implement it) over the same premise, with a representative sentence: the first 25 words of the first window's text followed by ` [P1]` stripped as `AuditVerifier` strips references. `--judge-scope all` (today) uses the whole premise; `--judge-scope cited` uses a premise holding only the cited passage (P1) with its heading, the change planned in S5.1b. Report the same token counts per judge call, and the ledger reservation per call (estimate plus `JUDGE_OUTPUT_RESERVE`; for generate, estimate plus `max_tokens`).
- R4 Totals: median and p90 over rows of tokens per call by purpose, and for three answer shapes (A: 1 generate + 2 judge; B: 2 generate + 3 judge; C: 3 generate + 6 judge, where block k of generate resends the prompt plus the earlier accepted sentences, estimate those as 40 tokens per earlier sentence) the ledger reservation per answer and answers a minute that fit in 8,000 (floor of 8000 / reservation). Print a short table and write `token-budget.json` and `token-budget.md` to `--out` (default `$CV_SCRATCH/s5-token-budget/out`).
- R5 Also state in the md, from reading the code (`providers/ledger.py`, `providers/rotation.py`): whether a reservation is replaced by the provider's actual usage after the call, how the 1.5x margin and the `max_tokens` reservation count against the minute window, and how long a reservation holds the window. Quote line numbers. This decides S5.1c and d.
- R6 Tests `tests/test_token_budget.py` on the fixture store (no real store, no network): the capturing rotation records a request and fails like `NoModelRotation`; `cited` scope produces fewer judge characters than `all` on a multi-window premise; the answers-a-minute arithmetic.
- R7 Run on the real data for `--judge-scope all` and `--judge-scope cited` and put both tables in your summary.
