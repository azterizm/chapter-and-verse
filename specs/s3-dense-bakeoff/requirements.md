- R1 Document text, `engine/chapterverse/dense/doctext.py`. `doc_text(doc_id) -> str` and an iterator over a doc-id range, from the opened `TextStore` and the router's `ConceptIndex`, deterministic. Text = an embedding-only prefix, then the heading, then the provision body text (read through the store's public methods for that coordinate), whitespace collapsed. Prefix form: `[<instrument short title with year, e.g. ERA 1996 or the full short title if no abbreviation is known>] [<Part or Chapter label and heading if the record holds one>] [<provision label and heading, e.g. s.124 Limit of compensatory award>]`; use only fields the store records already hold, and say in the summary which fields you used. Instrument docs (kind i): prefix with the title, then the instrument's long title or first provision headings if available; keep it simple and say what you did. Unit tests on the fixture store.
- R2 Embedder, `engine/chapterverse/dense/embed.py`. `OnnxEmbedder(model_dir: Path, *, pooling: Literal["cls","mean"], query_prefix: str = "", doc_prefix: str = "", max_tokens: int = 512, threads: int | None = None)` with `embed_docs(texts) -> np.ndarray[float32, (n, dim)]` and `embed_query(text)`, L2 normalised. Tokenise with `tokenizers` (truncation and padding set explicitly), run `onnxruntime` CPU with fixed intra-op threads, pool by the model's `1_Pooling/config.json` (bge: CLS; e5 and gte: mean over the attention mask). e5 prefixes: `query: ` and `passage: `; bge query instruction: `Represent this sentence for searching relevant passages: ` for queries only. A `load_model(name, models_dir)` helper verifies each file's sha256 against `models-manifest.json` before loading (fail closed). Batch in sorted-by-length order and restore the order. Unit tests with a tiny check: same text gives the same vector twice; norms are 1; a known-similar pair scores higher than an unrelated pair, for each model (skip if the model files are absent).
- R3 Bake-off, `eval/dense_bakeoff.py`, dev split only. For each dev row: BM25F candidates `router.discover(query, limit=50)`; pool = union over all dev rows of those candidates, every dev row's gold coordinates (as concept docs), and 30,000 provision docs sampled with `random.Random(20261122)` as distractors. Embed the pool once per model (cache embeddings as `.npy` under `$CV_SCRATCH/s3-dense-bakeoff/cache/<model>.npy` with the doc-id list). Per dev row, rank the pool by cosine to the query vector (dense-only) and also fuse with RRF: `score = 1/(60 + bm25_rank) + 1/(60 + dense_rank)`, where docs missing from a list get no term from it; take the dense top 50 for fusion. Score hit@1, hit@5, hit@10, MRR against gold with the same scorer the discovery gate uses (`eval/discovery_gate.py` loads the router's `eval/discovery.py`; reuse that), for: BM25F alone, each model dense-only, each model RRF. Also report each model's embedding throughput (docs per second, Mac CPU, threads used) and mean tokens per doc. Write `$CV_SCRATCH/s3-dense-bakeoff/report.json` and `report.md`. State clearly that dense-only within a pool is an optimistic estimate and that model choice uses RRF on dev.
