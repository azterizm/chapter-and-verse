# S3.3c Dense index, retriever and fusion into discovery: requirements

Context: master plan §5 stage 4 (`~/.claude/plans/plan-extensively-to-build-bright-sunset.md`), `reports/slice3-bakeoff-dev.md` (bge-small-en-v1.5 chosen: dev RRF hit@10 0.946, MRR 0.768 against BM25F 0.911 / 0.752). The full float32 corpus embedding is being built on Modal into `artefacts/dense/bge-small-en-v1.5.npy` (1,322,050 rows in concept doc-id order, 384 dims, L2 normalised) with `bge-small-en-v1.5.meta.json`; it may not be there when you start. Until it is, develop and test on the first 65,536 rows at `$CV_SCRATCH/modal-tp/bge-small-en-v1.5.npy` (doc ids 0 to 65,535) and on tiny indexes you build in tests. Query embedding is CPU only (`chapterverse.dense.embed.load_model`, `embed_query`).

Rules carried from Slice 2 that must not change: discovery never auto-binds (it offers chips); the out-of-scope and private-document checks run before discovery as now; `NoEvidence` (the negative-evidence receipt) is decided by BM25F alone, exactly as today: if `router.discover` returns no candidates or reason `no_match`/`no_terms`, the result is `NoEvidence` even if dense search has neighbours. With dense off, every output is byte-identical to today.

- R1 Index build, `build/dense_index.py --vectors NPY --store DIR --data-root ROOT --out DIR`: check row count equals the concept index `doc_count` and the meta's model revision; int8 scalar quantisation with one scale per dimension (`scale[d] = max_abs[d] / 127`, values rounded and clipped to [-127, 127]); binary codes = sign bits (`v > 0`) packed little-endian to 48 bytes per doc. Write `vectors.i8` (N x 384 int8), `codes.bin` (N x 48 uint8), `scales.f32` (384 float32) and `dense-manifest.json` with `files` (sha256, size), `model`, `revision`, model file sha256s from the meta, `dim`, `count`, `corpus_id` and `snapshot` of the store, `quantisation`. Deterministic output. Report sizes and seconds.
- R2 `engine/chapterverse/dense/store.py`: `class VectorStore(Protocol)` with `search(query: np.ndarray, k: int) -> list[tuple[int, float]]` and `count`. `BinaryInt8Store.open(dir, *, corpus_id)` verifies every file's sha256 against the manifest and that `corpus_id` matches (fail closed, `DenseLoadError`), memory-maps the files, and searches exactly (brute force, no approximate index): Hamming distance between the query's sign code and every code (XOR of uint64 views plus `np.bitwise_count`), keep the best `rerank` (default 1,000, ties broken by doc id), rescore those by `(int8_row * scale) . query` in float32, return the top `k` by score (ties by doc id). Optionally restrict to provision docs (`doc_id < first_instrument_doc`) if that is what BM25F candidates are; check what `router.discover` returns and match it.
- R3 `engine/chapterverse/dense/retriever.py`: `DenseRetriever(embedder, store, concepts)` with `search(text, k) -> list[DenseHit(doc_id, coordinate, heading, rank, score)]`; spans timed (query embed ms, search ms) and exposed for logging.
- R4 Fusion in `engine/chapterverse/discovery.py` `discover_step(..., dense: DenseRetriever | None = None, pool: int = 50, rrf_k: int = 60)`: with `dense` set, call `router.discover(query, limit=pool)`; apply the NoEvidence rule above from that BM25F result; otherwise fuse BM25F ranks and dense ranks (top `pool` each) by RRF `1/(rrf_k + rank)` summed, ties by BM25F rank then coordinate; return the top `limit` as `Suggest` with labels made as today (dense-only hits use `ConceptDoc.heading`); `confident` and the question text stay those of the BM25F result. With `dense=None`, the code path is today's, unchanged.
- R5 Wiring: `engine/chapterverse/app.py` reads `DENSE_DIR` and `DENSE_MODEL_DIR` (models dir with `models-manifest.json`); both set means load the store (verified, matching the text store's corpus_id) and the bge-small embedder (sha256 checked) at startup, log one line (count, load seconds), and pass a `DenseRetriever` to `Pipeline`; either unset means dense off and a log line saying so. No repo-path fallback. `Pipeline` passes it to both `discover_step` calls.
- R6 Gate tooling: `eval/discovery_gate.py` gains `--dense-dir`, `--models-dir` and `--split {dev,test}` (default `dev`); `--split test` refuses unless `--sealed-test` is also given (the orchestrator runs the sealed split once). Reports, for the pipeline with and without dense: hit@1/5/10 and MRR by source, and dense stage latency p50/p95 (embed and search separately).
- R7 Tests: quantisation round trip; exact search equals brute-force float ranking on a small random set when `rerank >= N`; Hamming tie order; manifest tamper and corpus mismatch fail closed; fusion order on a constructed example; NoEvidence unchanged when BM25F is empty even if dense has hits; dense off gives identical `discover_step` outputs to before on the fixture queries; app starts with dense off when the env is unset.
- R8 Measure on this Mac with the 65,536-row file (and the full file if present): index build seconds, `search` p50/p95 over 100 dev queries (embed and search separately), RSS added. Run the dev gate with dense if the full file is present; otherwise say so.
